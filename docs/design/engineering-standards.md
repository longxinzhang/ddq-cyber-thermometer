# 工程规范

## 目标

本规范用于约束项目代码组织、模块拆分、文件规模和 PR 变更边界。目标不是追求机械分层，而是让代码按功能模块清晰归属，便于后续维护、测试和评审。

## 模块拆分原则

代码应优先按功能模块拆分，而不是按类型名称或个人习惯拆分。一个模块应该围绕一类稳定职责组织代码，并尽量减少对其他模块内部细节的依赖。

建议的模块边界：

- App 启动与菜单栏生命周期：SwiftUI 入口、`AppDelegate`、菜单配置、应用退出。
- 系统监控与采样：CPU、内存、热状态、采样定时器和采样结果聚合。
- 传感器读取：温度、风扇、IOKit、外部命令 fallback。
- 顶栏渲染：状态栏图像尺寸、颜色、绘制逻辑。
- 更新能力：GitHub Release 查询、版本比较、下载、校验、安装脚本。
- 开机启动：`SMAppService` 状态读取、注册和取消注册。
- 共享模型与工具：值对象、格式化、Shell 执行、字符串转义等。

后续拆分 `Sources/MacHealthGuardian/main.swift` 时，优先按完整职责迁移类型，避免只把零散函数搬到“工具文件”里。一次 PR 如果既做行为变更又做大规模拆分，应尽量先提交纯拆分 PR，再提交功能 PR，降低评审风险。

## 文件规模控制

文件行数采用软限制加评审门槛，不用一个固定数字压所有文件。核心原则是：文件长度必须能被一个清晰功能边界解释。

建议标准：

| 文件类型 | 建议范围 | 评审门槛 | 处理要求 |
| --- | ---: | ---: | --- |
| 业务 Swift 文件 | 150-350 行 | 超过 400 行 | 说明原因，优先拆出独立职责 |
| 模型和值对象文件 | 80-250 行 | 超过 300 行 | 检查是否混入解析、网络或 UI 逻辑 |
| 渲染/UI 文件 | 150-400 行 | 超过 500 行 | 检查绘制、状态、交互是否应拆分 |
| 测试文件 | 150-400 行 | 超过 500 行 | 按被测模块或场景拆分 |
| Shell/构建脚本 | 80-220 行 | 超过 250 行 | 抽函数或拆脚本，保持入口清晰 |
| 生成型脚本/素材脚本 | 按实际复杂度 | 超过 500 行 | 允许例外，但需有清晰分段 |

强制要求：

- 新增业务代码文件不应一开始就超过评审门槛。
- 修改已有超大文件时，如果改动触达一个可独立命名的职责，应优先顺手抽出完整类型或完整功能块。
- 超过评审门槛但暂不拆分时，PR 描述或设计文档应说明原因和后续拆分方向。
- 不为降低行数而制造过细文件。一个文件只包含少量代码但无法独立表达功能边界，也不算好的拆分。

## 文件命名与目录建议

Swift 文件应使用能表达职责的名称。后续源码目录可按模块逐步演进为：

```text
Sources/MacHealthGuardian/
├── App/
├── Monitoring/
├── Sensors/
├── Rendering/
├── Updates/
├── LaunchAtLogin/
├── Models/
└── Support/
```

拆分时优先保持小步迁移：

- 一个文件移动只承载一个明确模块。
- 类型移动后不改变行为，除非 PR 明确声明。
- 与系统 API 或外部命令交互的代码，尽量隔离在模块边界内，便于测试时替换。
- 纯逻辑和值对象优先放入可被测试 target 依赖的核心模块，避免长期滞留在 `@main` 入口文件中。

## PR 变更边界

每个 PR 应能用一句话说明主要目的。以下变更应尽量避免混在同一个 PR：

- 大规模文件拆分和用户可见功能变化。
- 构建/发布脚本调整和运行时逻辑调整。
- 纯格式化和行为修改。
- 无关文档整理和核心代码改动。

如果确实需要混合变更，PR 描述应明确拆分原因、风险点和测试覆盖。

## 文档要求

以下情况需要同步更新设计文档或 README：

- 模块目录结构发生变化。
- 构建、打包、发布流程发生变化。
- 测试命令、测试范围或验证标准发生变化。
- 新增影响用户使用方式的功能。
- 新增需要权限、网络、系统 API 或外部命令的能力。

## 例外处理

允许例外，但例外必须可解释：

- 系统 API 桥接代码因类型定义集中而较长。
- 素材生成脚本为保持渲染上下文集中而较长。
- 临时过渡阶段保留超大文件，但必须有后续拆分路径。

例外不是长期豁免。超过评审门槛的文件在后续相关改动中应持续收敛。
